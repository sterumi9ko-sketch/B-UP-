# UP 主风格评分标准（打分前必读）

本文件说明 `src/data/ups.ts` 里每位 UP 主 8 个维度分数是怎么来的。
目的只有一个：**让任何人都能复核一个分数为什么是高、为什么是低**，而不是凭感觉给分。

---

## 一、评分只依据公开内容

允许作为依据的：

- 公开投稿的标题、简介、标签、分区
- 公开的合集/系列名称（例如「XX 逐帧解析」「新番导视」）
- 公开的空间签名、认证信息、粉丝数快照
- 公开的第三方资料（百科条目、媒体报道），需要在 `sources` 里写明

**不允许**作为依据的：对 UP 主私人生活、真实心理状态、性格缺陷的推测或评价。
本站分数描述的是「作品呈现出来的创作方式」，不是「这个人是什么样的人」。

---

## 二、0–100 分档定义

| 档位 | 分数 | 含义 | 判断口径 |
|---|---|---|---|
| S | 88–100 | 标志性特征 | 几乎每条投稿都能体现，是该 UP 主最好辨认的特点 |
| A | 74–87 | 明显倾向 | 大部分作品体现，是其内容的主要手法之一 |
| B | 58–73 | 中等偏上 | 经常出现，但不是主要内容驱动力 |
| C | 42–57 | 中性 / 偶发 | 偶尔出现，或随选题变化 |
| D | 0–41 | 基本不涉及 | 极少出现，或与其内容取向相反 |

给分时先在表里找到最贴近的档位，再在档位区间内微调（例如「很明显的 A，接近 S」给 86）。

---

## 三、8 个维度的打分细则

### 1. 幽默整活（humor）
- **88+**：笑点是内容的核心驱动，标题本身就在玩梗，节奏围绕包袱设计
- **74–87**：稳定输出段子/吐槽，幽默是主要看点之一
- **58–73**：经常开玩笑，但信息量才是主体
- **42–57**：偶尔幽默，整体偏平实
- **≤41**：表达严肃或学术化，几乎不靠笑点推进

### 2. 深度考据（research）
- **88+**：逐帧/逐集考据，引用原作、访谈、设定资料，形成系列化考据内容
- **74–87**：经常查资料、比对细节、解释背景设定
- **58–73**：会做基本的事实核查与背景补充
- **42–57**：以观感与结论为主，偶有考证
- **≤41**：基本不做资料考据

### 3. 情绪共鸣（empathy）
- **88+**：内容主线就是情绪体验，围绕"被打动"的瞬间展开
- **74–87**：经常分享个人情感反应与代入体验
- **58–73**：会表达喜好与情绪，但以内容分析为主
- **42–57**：偏理性叙述，情绪表达较少
- **≤41**：情绪表达基本不出现在作品里

### 4. 观点表达（opinion）
- **88+**：有明确评价体系，敢下判断并给出理由，常做批评与排名
- **74–87**：稳定给出个人评价与立场
- **58–73**：有观点，但以介绍和描述为主
- **42–57**：偏中立叙述，少下判断
- **≤41**：几乎只做信息传递，不做评价

### 5. 叙事创作（narrative）
- **88+**：内容高度结构化，重视起承转合、节奏与剪辑设计
- **74–87**：明显为内容设计结构与高潮
- **58–73**：有基本结构意识，不刻意设计
- **42–57**：直述信息，结构简单
- **≤41**：基本为素材堆叠或流水记录

### 6. 社群互动（community）
- **88+**：把观众当作共同话题的参与者，常互动、发起讨论、回应评论
- **74–87**：经常与观众互动，推荐、提问、承接评论梗
- **58–73**：有互动意识，但以单向输出为主
- **42–57**：互动较少
- **≤41**：接近纯单向资料输出

### 7. 实验创新（experiment）
- **88+**：持续做冷门题材、反常形式或有风险的选题，把"新鲜"当硬指标
- **74–87**：经常尝试新形式或冷门内容
- **58–73**：偶尔尝试，主要做成熟题材
- **42–57**：偏好稳妥选题
- **≤41**：内容形式高度固定，以热点和主流题材为主

### 8. 审美表达（aesthetic）
- **88+**：专门讨论作画、演出、分镜、配乐等视听层面，有明确审美判断
- **74–87**：经常涉及视听层面的分析
- **58–73**：会提到画面与配乐，但不是重点
- **42–57**：以剧情和信息为主，少谈视听
- **≤41**：基本不涉及视听层面的讨论

## 四、打分时的自检问题

给一位 UP 主打完分，请回答：

1. 每个 ≥74 的维度，能否在 `observedStyle` 或 `scoreRationale` 里用**公开作品**举例说明？
2. 每个 ≤41 的维度，是否确认过该 UP 主确实不常做这件事，而不是"我没看到"？
3. 8 个维度里是否有超过 5 个都挤在 70 分以上？如果有，说明区分度不足，需要重新对照分档表。
4. 如果两位 UP 主的分数向量几乎相同，说明评分没有体现差异，需要复核。

上面第 3、4 条都有对应的自动化测试（见 `tests/ups-data.test.ts`）：

- 每位 UP 主画像的最高分与最低分至少相差 20 分
- 任意两位 UP 主的画像不能完全相同

## 五、改完之后要做的两件事

### 1. 跑测试

```bash
npm test
```

数据完整性用例会拦住大部分低级错误（分数越界、画像过于平均、缺少来源等）。

### 2. 重新校准相似指数

**这一步容易被忽略，但很重要。**
如果你大幅调整了 UP 主分数（或增删了题目），分数分布会整体移动，
可能导致所有人的相似指数都偏高或偏低。用校准脚本重新测一次：

```bash
node scripts/calibrate.mjs
```

它会输出「用户画像 → UP 主画像」的距离分布，以及不同 `maxDistance` 下的分数区间。
把合适的值填回 `src/config.ts`：

```ts
match: {
  maxDistance: 145,   // 决定分数刻度，见脚本输出
  minSimilarity: 30,  // 分数下限
},
```

> 当前值 145 的由来：实测「每个用户最接近的 UP 主」距离为 21（很近）到 94（较远），
> 取 145 后分数自然落在约 35~90 之间，既有区分度也不会大量挤在下限。

## 六、计分与匹配的口径（与代码一一对应）

| 环节 | 实现位置 | 说明 |
|---|---|---|
| 7 档分值 | `src/config.ts` → `test.scale` | 完全认同 +3 … 完全不认同 −3 |
| 反向题取反 | `src/core/scale.ts` → `scoreForAnswer()` | 反向题的分值乘以 −1 |
| 维度原始分 | `src/core/scoring.ts` → `computeRawScores()` | Σ（单题得分 × 题目权重） |
| 可达上下界 | `src/core/scoring.ts` → `computeDimensionRanges()` | 用真实可达范围，保证 50 分 = 中性 |
| 标准化 0~100 | `src/core/scoring.ts` → `normalizeRawScores()` | 线性映射并夹到 [0,100] |
| 维度权重 | `src/core/match.ts` → `computeDimensionWeights()` | 题目权重和，再归一化到平均值 1 |
| 加权距离 | `src/core/scoring.ts` → `weightedEuclideanDistance()` | √(Σ 权重 × 差²) |
| 相似指数 | `src/core/scoring.ts` → `distanceToSimilarity()` | (1 − d / maxDistance) × 100，夹到 [30,100] |
| 排序 | `src/core/scoring.ts` → `buildRanking()` | 相似指数 ↓ → 距离 ↑ → UID ↑（保证可复现） |

## 七、数据结构约定

每位 UP 主的档案包含：

| 字段 | 说明 |
|---|---|
| `id` | 站内编号 `up_001`…，用于图片文件名 |
| `uid` | B 站数字 UID，来自公开搜索/空间接口核实 |
| `name` | 昵称 |
| `category` | 内容分类（7 类之一） |
| `tags` | 3–5 个风格标签 |
| `summary` | 一句话风格总结 |
| `intro` | 较长的创作风格介绍 |
| `contentFocus` | 主要创作内容说明 |
| `observedStyle` | 基于公开投稿可观察到的表达特征（列表） |
| `scores` | 8 维分数（按本文件标准） |
| `scoreRationale` | 评分依据，说明为什么给这些分 |
| `sources` | 公开资料来源（含链接与查证时间） |
| `verification` | `verified` / `partial` / `unverified` |
| `fansSnapshot` | 公开粉丝数快照 |
| `verifiedAt` | 核实时间 |
| `image` | 可选，自定义图片文件名 |
| `matchable` | 是否参与匹配 |

`verification` 的取值会直接影响结果页提示：

- `verified`：昵称、UID、公开投稿内容都经接口核实
- `partial`：昵称与 UID 已核实，但部分字段（如完整投稿列表）未取到
- `unverified`：占位数据。**只要名单里还有 `unverified` 且 `matchable: true`，结果页会显示醒目提示**，提醒用户结果仅供参考
